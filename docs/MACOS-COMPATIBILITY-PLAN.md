# macOS compatibility review and implementation plan

> **Status as of 2026-10-18 (v0.4.59): reference; nothing implemented.** No phase below has started. The only platform-aware code outside Windows gates is the chat panes' CLI lookup (`src/chat/shared/findCli.mjs`, which already resolves darwin binaries). The evidence column now names current functions instead of 0.4.9 line numbers, and the Windows-only surfaces added since 0.4.9 (clipboard capture, the picker's paste-back, the Chrome extension's native host, the Jump List, the chat panes' bundled CLI) are rows of their own. The port is listed in `docs/UPGRADE-PLAN.md` → **Open now**. Current architecture is `CLAUDE.md`; release history is `CHANGELOG.md`.

Reviewed 2026-09-18 against commit `11abcd2`, version 0.4.9. The file was committed later, unchanged, with 0.4.46–0.4.47 (`ad6d7ba`); its estimates and assessment are as of 0.4.9. This is a source review and implementation proposal, not a completed port. No application code was changed. Baseline verification on Windows at the time: the test suite, typecheck and production build passed. No macOS runtime, packaging, credentials, or permission flow was exercised.

**Assessment**

macOS support is feasible without rewriting the product or replacing Electron. The app has accumulated substantial Windows integration, but the monitoring architecture is largely portable: authenticated hook events, the reducer, provider identities, usage parsing, worker protocol, optional MongoDB history, React panes, layout persistence, and xterm rendering can stay.

The work is concentrated around the operating-system boundary, although that boundary currently reaches into main, hooks, shared path helpers, and renderer input handling. Changing `electron-builder --win` to `--mac` is insufficient. The best first release is the existing embedded workspace on Mac, with explicit fallback behavior for external sessions. Exact external-window switching should be a separately scoped feature.

Planning estimates for one engineer familiar with this repository, assisted by coding tools, with an Apple Silicon Mac available from day one:

| Outcome | Cumulative effort | Included |
| --- | --- | --- |
| Feasibility spike | 1–2 engineer-days | Packaged app opens, native PTY and usage worker run, one real hook round trip |
| Useful internal Apple Silicon beta | 10–15 engineer-days / 2–3 weeks | Embedded shells and agents, resume, monitoring, paths, Mac input/lifecycle, basic launches, truthful credential/focus fallbacks |
| Distributable Apple Silicon release | 15–25 engineer-days / 3–5 weeks | Beta plus signed/notarized distribution, clean-install/update testing, CI and operational documentation |
| Selected external terminal/editor focus integrations | Add 5–15 engineer-days | Permission-aware native discovery/focus for explicitly selected apps |
| Intel qualification | Add 2–4 engineer-days if straightforward | Separate native build/runtime/update validation; more if native dependencies differ |

These are judgment ranges, not measured task durations or promises. Apple enrollment/provisioning delays and time waiting for testers are excluded. Broad parity across arbitrary terminal apps/tabs cannot be estimated credibly before a Mac focus spike. The main unknowns are shell-profile compatibility, credential access under a signed identity, and external-session-to-window mapping.

**Recommended compatibility boundary**

Keep one application and one renderer. Extract a small main-side platform module, selected once at startup, responsible for shell launch specs, external launches, window discovery/focus, OS attention, and supported capabilities. Keep pure path and shortcut policies separately testable. Credential providers should be asynchronous services, not renderer APIs.

Expose only platform name, display accelerators, and useful capability states through the existing validated preload surface. A capability should distinguish unsupported, available, and permission-required states where relevant. Menus, palette, settings, tray and daemon behavior must agree; do not scatter `process.platform` checks throughout components.

Do not move the reducer, daemon, usage parsing or layout engine behind generic platform abstractions. They are already suitable shared code. Preserve existing auth validation, hook deadlines, provider identity and usage attribution, worker crash isolation, bounded quit flushing, and Windows behavior.

**Implementation sequence and completion gates**

1. **Prove the native runtime on a Mac (1–2 days).** Add a minimal Mac packaging target in the implementation branch, exclude Windows-only resources, gate OS-only calls, and build on Apple Silicon. Verify node-pty spawns zsh from inside the packaged app and utilityProcess reads a synthetic usage fixture from asar. Send a real local provider event through a test endpoint. Keep this spike small; its result should revise the estimates before broad work.

2. **Extract platform policy and unify paths (2–3 days).** Preserve the Windows adapter and add Mac capability fallbacks. Unify app-data/endpoint/provider-directory resolution for installer, bridge, main and tm. Fix POSIX identity semantics and persisted-key migrations. Gate native resource staging and Win32 focus discovery. Completion: external CLI hooks and embedded hooks reach the same daemon with custom ports and paths containing spaces; case-distinct projects never merge.

3. **Deliver the embedded terminal workflow (3–4 days).** Implement zsh startup/profile/cwd hooks and a tested bash path. Resolve shell/Node/provider executables for GUI launches, including Homebrew and version-manager installations without globally rewriting PATH. Preserve custom profiles and avoid a fixed sleep as shell-readiness detection. Completion: create, resize, paste, interrupt, hide/show, reattach after renderer reload, close, change cwd, quit/restart and resume the correct Claude/Codex session. Test daemon-created headless terminals as well as visible panes. Confirm quit does not leave owned agent processes running accidentally.

4. **Make the Mac application coherent (2–3 days).** Implement keyboard/menu, tray/Dock/activation, material and notification adapters. Add basic external app launches and graceful errors. Handle the six-pane-full fallback: it currently opens an external terminal, so either support that launcher before beta or provide an explicit capacity result without losing the requested action. Route clicks on embedded agents and notifications to their actual panes; main's notification focus path currently only attempts native focus. Completion: no dead Windows-only controls, no permission prompts needed just to monitor embedded sessions, and normal terminal keys remain intact.

5. **Integrate credential availability (2–3 days).** Probe the installed provider's actual supported storage on the Mac; do not guess Keychain service/account identifiers from Windows code. Implement minimal, bounded credential reads with no token logging, prompt storms or new plaintext exports. Cache status, refresh on relevant changes and handle revoked/expired credentials. Completion: working quota meters for the qualified storage mode, or an accurate unavailable explanation while local spend/live hooks still work. A locked/denied keychain must not block startup or the one-second snapshot.

6. **Ship and qualify (5–10 days).** Add macOS CI and clean-machine smoke tests; make Windows checks mandatory alongside them. Build/sign/notarize the app and its required native helpers, produce DMG and ZIP and verify `latest-mac.yml`. Exercise an actual update between two signed versions, preserving staged hooks and settings. Test a Finder launch with no development shell environment, fresh login and permissions denied, application move/update, and macOS restart. Update README, CLAUDE.md, hooks/SKILL.md, tm help and diagnostics. Keep the existing Windows release creation-before-publish rule and avoid artifact/feed collisions between build jobs.

Phases 1–5 total 10–15 engineer-days; phase 6 brings the cumulative range to 15–25 days. Credential backend support that exceeds the qualified beta storage modes or an external focus requirement increases the scope.

**External focus: a separate decision**

Embedded sessions are the strongest Mac route because `TM_TERMINAL_ID` already provides precise pane association without operating-system window inspection. Make that path fully reliable first.

For an external session, separate three different guarantees: launching an app, activating an existing app, and selecting the exact terminal window/tab containing an agent. Successful application activation does not prove exact session focus. A PID or a window title alone can be ambiguous, especially with multiple windows/tabs, Electron helpers, or reparented shells.

For the beta, keep monitoring external sessions but advertise focus availability accurately. If a target cannot be identified, open the workspace and show the relevant agent; do not launch a duplicate agent as a focus fallback. The window palette should omit unsupported entries or explain unavailable access.

For fuller integration, run a bounded spike against an agreed list (for example Terminal.app, iTerm2 and Cursor). Evaluate NSWorkspace for app activation and Accessibility APIs for window enumeration/raising, plus app-specific terminal identifiers where available. Electron provides an Accessibility trust check, not a ready-made equivalent of this project's Win32 process/window resolver. Permission request and denial recovery belong in the app after explicit feature use, never inside a short-lived lifecycle hook. Apple Events automation can introduce its own permission flow. Do not assume Screen Recording is necessary; determine it from the chosen implementation.

Keep any optional discovery out of the hook critical path unless it demonstrably fits the existing 180 ms total bridge deadline and 75 ms discovery budget. A main-owned asynchronous resolver/cache is preferable to prompting or doing unbounded native work on each hook. Revalidate target ownership before focus, handle exited targets, and use an explicit unsupported result for terminal tab combinations the adapter cannot distinguish. A signed helper introduces its own packaging and permission-identity work.

**Verification matrix**

| Layer | Required evidence before claiming support |
| --- | --- |
| Shared unit/contract tests | Windows and POSIX endpoint paths; custom provider homes; roots/trailing slashes; case sensitivity; launch quoting with spaces, quotes, dollar signs and backticks; chunked cwd reports; capability/IPC validation; credential unavailable states |
| Hook integration | Claude/Codex/Cursor install, repair, remove preserve unrelated hooks; standalone versus Settings installation; app stopped and stale endpoint; trust workflow; staged runtime after upgrade; hook failure never fails provider command |
| Terminal runtime | zsh and supported bash profiles; missing CLIs; Unicode/bracketed paste; Ctrl+C; Command+C/V; image clipboard; large output and resize; changed cwd/exact resume; six panes; headless daemon terminal; renderer crash; quit cleanup |
| OS integration | menu-bar icon in light/dark modes; Dock activation/minimize/hide/quit; shortcut conflict; notifications; login without unwanted workspace; lock/suspend/wake; multiple displays, scaling, Spaces/full-screen apps; permissions denied |
| Usage/data | real Mac provider fixture scans and worker recovery; local usage without subscription auth; optional Mongo absent/offline; notes save/watch; project grouping on a case-sensitive volume; the pace streaks (the one GPU layer left) render or degrade cleanly; clip store sealing and capture-off fallback |
| Packaged app | native binaries and helper signatures/permissions; asar worker; fresh Finder launch; signed/notarized install; a real signed upgrade; hook runtime survives update; correct architecture/feed |
| Windows regression | existing typecheck/test/build gates plus PTY, focus, hook repair and NSIS/update smoke tests; retain PowerShell startup and Windows path semantics |

The passing Windows test suite is useful baseline evidence, not proof of Mac compatibility. Some tests embed Windows fixtures and native availability assumptions; run and classify failures on Mac rather than globally skipping native coverage. Choose the minimum supported macOS release from the pinned Electron version's documented support and test it; do not promise compatibility with every older Intel Mac by default.

**Source checks informing the plan**

- Electron's [app API](https://www.electronjs.org/docs/latest/api/app) documents macOS appData under `~/Library/Application Support` and platform-specific lifecycle/login behavior. This supports consolidating discovery with Electron rather than retaining APPDATA fallbacks everywhere.
- Microsoft's [node-pty repository](https://github.com/microsoft/node-pty) supports macOS. Locally, the installed package additionally contains both Darwin prebuild directories; their execution/signing remains to be verified on Mac.
- Claude Code's [credential management documentation](https://code.claude.com/docs/en/authentication#credential-management) documents macOS Keychain storage, a file fallback when Keychain writes fail, and `CLAUDE_CONFIG_DIR`. This explains why the current file-only reader is insufficient.
- Codex's [authentication documentation](https://developers.openai.com/codex/auth) documents file, keyring, automatic and ephemeral storage. The account RPCs no longer depend on which one is used (0.4.79); the remaining auth.json existence checks cannot cover all these configurations.
- Electron's [systemPreferences API](https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesistrustedaccessibilityclientprompt-macos) provides the Accessibility trust check needed for an optional external-window integration.
- electron-builder's [Mac target documentation](https://www.electron.build/mac/), [auto-update documentation](https://www.electron.build/docs/features/auto-update/) and [notarization documentation](https://www.electron.build/docs/notarization/) inform DMG/ZIP distribution and signing requirements. The installed builder schema and `electron-updater/out/MacUpdater.js` were also inspected; exact configuration should target the lockfile version, not blindly copy newer examples.

Recommendation: retain this codebase, target Apple Silicon and the embedded workspace first, and use the first two days on a real packaged Mac spike. The Windows investment is largely reusable; precise external desktop control is the part that needs a new platform implementation and the most deliberate scope control.
