# 4.2 plan — chrome diet and the launch journey

Working notes for the 0.4.2 pass. Checkboxes are the source of truth for what
has landed; update them as work lands so a fresh session can pick this up.

## The journey we are designing for

1. Summon the workspace (hotkey).
2. Point it at a project — the one the last session was in, home, a live
   project, or a folder dropped from Explorer.
3. Start an agent there: Claude Code or Codex (a plain shell is the fallback).
4. Work in the pane; watch the Agents pane; answer whatever is waiting.
5. Occasionally: check limits/spend, open the project in Cursor, rebuild the app.

Everything on the launch path (steps 2–3) should be a single obvious row. Everything
else is secondary and should sit one level away — a menu, a popover, the palette.

## What got in the way (audit, 2026-09-08)

| Where | Problem | Decision |

Rule of thumb that falls out of this: **the title-bar menus hold verbs, the status
bar holds state.** Toggles and modes (which panes, size, columns, layout) are
status-bar popovers, like an IDE's bottom bar; actions that *do* something
(new, open, run, quit) are menus. Both are always mirrored in the palette.

## Status bar (bottom)

Left → right: **Update** (rebuild & relaunch, with main's reply beside it) ·
**Panes ▴** (Agents / Usage / Activity, then Limits / Open windows) ·
**Layout ▴** (Workspace size: Full / Left half / Right half; Columns: Auto / 1 / 2 / 3;
Saved layouts: save current…, apply, delete; Reset pane sizes) · spacer ·
`CDP :port` (only when launched for automation) · `v0.4.x`.

The Layout chip's label shows the live state (`Full · Auto`), so the bar reads as
state even when closed.

## Suggestions for the next pass (UI/UX)

- **Waiting sessions should be one click from anywhere.** The `2 waiting` chip filters the list; it should *go there* (next waiting session, Ctrl+Shift+W) on click and filter on Shift-click. Same for the tray tooltip.
- **The launch row could remember per project.** `tm.launch.v1` is one global default; a project you always run Codex in should start Codex when it is the target.
- **Project switcher: show recents inline.** Two or three most-recent projects as small chips under the switcher would remove one click from the launch path for the common case.
- **Open windows section → palette only.** It is collapsed by default and the palette's `#` prefix raises any window. Dropping it from the sidebar leaves Limits as the single sidebar view.
- **Terminal pane title should show the live folder** now that main tracks it (`term:cwd`), not the launch label — a pane that has `cd`'d away should say so.
- **Digest strip after a long absence** could offer the top action ("api-gateway asked a question 12m ago — go") rather than a summary sentence.
- **First-run state**: if no hooks are installed, the empty grid should say so and offer *Install hooks* instead of the generic hint.
- **Settings is a modal; most of it is state.** Hotkey, startup, notifications could become a fourth status-bar popover eventually, leaving the modal for hooks and diagnostics.
- Parked: machine memory/GPU in the status bar — the bar should stay about the workspace, not the machine.
